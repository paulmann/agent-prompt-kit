# Валидация по исходной цели

Набор существует из-за одного запроса. Эта страница проверяет тот запрос по доставленным артефактам,
требование за требованием, и прямо говорит, что проверено, а что остаётся предположением. Это ответ
на вопрос «сделано ли то, что просили», не зависящий от памяти автора.

## Цель, переформулированная

> Превратить исходный запрос пользователя в универсальный переносимый системный промпт для
> ИИ-агента, который умеет: (1) определять тему и нужные навыки из текущей переписки, (2) собирать и
> синтезировать релевантный контекст из других переписок или предоставленных источников,
> (3) работать как специалист по теме, не зашивая один домен, и (4) использовать агента GitHub Wiki
> Writer, чтобы создать новый репозиторий с финальным промптом и документацией — с идентичностью,
> навыками, правилами контекста, правилами инструментов и безопасности, форматом вывода, чек-листом
> QA и примерами; каждый Markdown-файл — по-английски плюс русская версия; без выдуманного
> контекста; с явными предположениями; с модульными проверяемыми инструкциями; с финальной
> валидацией до публикации.

## Что проверено, а что предполагается

Ясность здесь важнее чистой таблицы.

**Проверено командой или артефактом**

- последовательность модулей `M0`…`M13` на месте, по порядку, по одному разу;
- 14 строк `**Check:**`, по одной на модуль;
- 9 инвариантов с номерами;
- у каждого Markdown-файла есть русская пара, у каждой пары — английский оригинал;
- нет `{{placeholder}}` вне блока кода, нет литералов, похожих на секреты, нет абсолютных путей;
- нет висячих ссылок `M<число>` ни в одном документе;
- нет битых относительных ссылок;
- `version` промпта равна свежей версии в `CHANGELOG.md`;
- репозиторий проходит проверки набора `doc`, `audit`, `assets` и `privacy`.

**Предполагается, не доказано**

- что карточки *снижают* дрейф в конкретной модели — механизм правдоподобен, примеры показывают его
  в работе, но контролируемого замера нет;
- что трёх примеров достаточно, чтобы научить форме — выбрано по стоимости, достаточность не
  измерялась;
- что пятнадцати минут хватает на карточку действительно незнакомого домена — это пол, а не
  потолок;
- **что модель следует правилу доставания при непустом хранилище** — довод о стоимости и есть причина
  так думать, и одна команда — самая дешёвая возможная форма, но контролируемого сравнения не было;
- **что лексического поиска достаточно на практике** — совпадение синонимов потеряет хорошую запись;
  измерено только, что несовпадающий запрос возвращает пусто, а не шум.

Эти три названы предположениями, а не результатами. Страница валидации, утверждающая обратное, сама
была бы режимом отказа 11 из промпта.

## Кто что делал

| Шаг | Исполнитель |
|---|---|
| Дизайн промпта, контракт модулей, линтер | эта сессия, инструментарием набора GitHub Wiki Writer |
| Структура репозитория, документация, изображения | опубликовано командами набора (`assets render`, `doc`, `audit`, `wiki build`) |
| Независимое ревью по этим контрактам | `tools/external_check.py` — загружает опубликованные байты и заново считает якоря, разделы, типы журнала, порядок модулей и шапку изображения, не читая локальное дерево |
| Публикация | `gh` под идентичностью владельца; коммиты подписаны владельцем |

### Попытка делегирования и почему она записана здесь

Планировалось, что независимое ревью выполнит Saved Agent «GitHub Wiki Writer». Он был вызван трижды
— два раза с узким брифом «только веб» и один раз с диагностикой в одну строку (сколько заголовков
модулей в файле) — и все три прогона упали на исполнении (`subagent_execution_failed`), не выдав ни
одной находки. Это записано, а не скрыто, по трём причинам: ревью всё равно состоялось и должно быть
приписано верно; заявление о ревью агентом, которого не было, было бы режимом отказа 11 из самого
промпта (театр авторитета); следующему человеку полезно знать, что маршрут делегирования сейчас
сломан для этого агента, а не открывать это заново. Отказ на уровне слоя исполнения хоста, а не в
брифе: третий запрос требовал одного предложения об одном файле и упал так же.

Замещающая проверка слабее в одном: она проверяет структуру и опубликованные байты, а не суждение;
и сильнее в другом — она читает ровно то, что читает потребитель репозитория.

## Как прогнать валидацию заново

```bash
python tools/prompt_lint.py                     # структурные контракты, локальное дерево
python tools/prompt_lint.py --json | head -40   # находки машинно
python tools/experience.py selftest             # 13 проверок хранилища, каждая на фикстуре
python tools/experience.py check                # поставляемое хранилище, если записи есть
python tools/external_check.py                  # те же контракты по опубликованным байтам
```

Ожидается на опубликованном дереве: обе команды возвращают `0`. Внешняя проверка ещё и заново
считает якоря заголовков и читает шапку PNG, поэтому свежий клон не считается доказательством того,
что отдаёт GitHub.
